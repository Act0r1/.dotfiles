# project.build.yaml

Используй этот скилл для работы с файлом `project.build.yaml` в корне подключённого Git-репозитория.

Перед созданием или ревью файла прочитай [полную спецификацию](references/specification.md).

## Рабочий процесс

1. Изучи файлы репозитория и определи движок, точку входа, менеджер зависимостей и доступные команды сборки. Не выдумывай команды, если их можно получить из `package.json`, `pyproject.toml`, `requirements.txt`, `go.mod`, `composer.json` или структуры проекта.
2. Создай или обнови только `<repo-root>/project.build.yaml`.
3. Всегда указывай `version: "1.0.0"`.
4. Задай `entrypoint` с учётом движка. Для Nginx используй `entrypoint: ""`. Не помещай в `entrypoint` сложную shell-команду: `deploy-service` делит значение по пробелам и не обрабатывает внутренние кавычки как shell.
5. Расположи стадии в порядке выполнения. Не добавляй стадию `deploy`: её автоматически создаёт `api-gate`.
6. Каждый элемент `stages[].steps` записывай строкой с shell-командой, а не объектом `{ command: ... }`. Команды выполняются последовательно из `/workspace`; ошибка останавливает сборку.
7. Заключай команду в YAML-кавычки, если она содержит двоеточия или другие YAML-значимые символы.
8. Добавляй `status_pages` только при необходимости. Принимай HTTP-коды `400–599` и непустые абсолютные URL-пути, начинающиеся с `/`. Коды записывай в кавычках.
9. Проверь итоговый YAML по спецификации и структуре репозитория. Не запускай команды из стадий без прямой просьбы пользователя.

## Минимальная форма

```yaml
version: "1.0.0"
entrypoint: app.py
stages:
  - name: build
    steps:
      - pip install -r requirements.txt
```

## Критические ограничения

- Имя файла строго `project.build.yaml`, расположение — корень репозитория.
- Поддерживается только версия `1.0.0`.
- `steps` — массив строк.
- Рабочий каталог сборки — `/workspace`.
- Служебные UUID, данные приложения, репозитория и окружения в файл не добавляются.
- Некорректные элементы `status_pages` игнорируются `api-gate`, поэтому выявляй их при ревью.
